# NotePalette 将来構成の選択肢

最終更新: 2026-10-02

## この文書の目的

NotePaletteを今後長く使う中で、現在のElectron版を継続するか、より軽量なWindowsネイティブ版へ移行するかを判断するための資料です。

現時点で移植を決定するものではありません。現在のElectron版には十分な機能があり、通常利用に問題がなければ、そのまま改良を続けるのが最も低コストです。

## 想定する理想的な配布形態

```text
NotePalette/
├─ NotePalette.exe
└─ NotePaletteData/
```

- アプリ本体は、できれば単独の `NotePalette.exe`
- メモ、画像、配置、バックアップは `NotePaletteData` に分離
- 別PCへはフォルダごとコピーすれば利用できる
- インストーラーや管理者権限を必須にしない
- アプリを更新しても利用データを消さない

完全な「1ファイルだけ」にすると、更新され続けるメモや画像までexeへ入れる必要があり、破損や更新の扱いが難しくなります。そのため、実用上は「単独exe＋データフォルダ」が扱いやすく安全です。

## 現在のElectron版

### 長所

- 現在のHTML、CSS、TypeScriptの実装をそのまま育てられる
- 画面の変更や機能追加が比較的速い
- ドラッグ＆ドロップ、自由配置、タブなどを実装しやすい
- すでに主要機能とバックアップ機能が動作している

### 短所

- 配布フォルダが大きい
- Electron本体と関連ファイルが必要で、exe単体にはしにくい
- 起動時間とメモリ使用量はネイティブアプリより大きい
- 数MB以上の巨大テキストを一度に表示する用途には不向き

### 継続が適している条件

- 現在の起動速度とメモリ使用量に大きな不満がない
- 個人利用が中心
- 新機能や操作性の改善を優先したい
- 配布時にフォルダ一式をコピーする運用で困らない

## 第一候補: C# + .NET + WPF

Windows専用の軽量版を作る場合の第一候補です。

### 期待できること

- 自己完結型・単一ファイルとして `NotePalette.exe` を発行できる
- Electronより配布容量とメモリ使用量を抑えやすい
- 起動を速くしやすい
- Windowsのファイル操作、クリップボード、ショートカットと相性がよい
- 大きなテキストを扱う専用部品や仮想化を導入しやすい
- 長期的に安定したWindowsデスクトップアプリを作りやすい

### 注意点

- 画面はXAML、処理はC#を中心に作り直す必要がある
- 現在のHTML/CSSの画面をそのまま移植することはできない
- 単一ファイル発行でも、.NETランタイムを内包するためexeは数十MB規模になり得る
- ネイティブDLLを使う機能を追加すると、関連ファイルが必要になる場合がある

### 適した配布方式

- `.NET 自己完結型`
- `単一ファイル発行`
- `Windows x64` を対象
- 利用データはexe横の `NotePaletteData` に保存

## 第二候補: C# + Avalonia UI

将来、Windows以外でも同じアプリを使いたくなった場合の候補です。

### 長所

- C#で開発できる
- Windows、macOS、Linuxを対象にできる
- WPFに近い考え方で画面を作れる
- 自己完結型の配布が可能

### 注意点

- Windows専用ならWPFのほうが情報量と実績が多い
- OSごとの差を確認するテストが増える
- Windows固有機能との連携はWPFよりひと手間かかる場合がある

## 第三候補: Rust + Tauri

現在のWeb画面の考え方をある程度残しながら、Electronより軽量にする候補です。

### 長所

- HTML、CSS、TypeScriptの知識や一部設計を活かせる
- Electronより配布容量とメモリ使用量を抑えやすい
- ファイル保存などの中核処理をRustで堅牢に実装できる

### 注意点

- WindowsではWebView2に依存する
- RustとWeb画面の両方を扱うため、開発と障害対応が複雑になる
- UIがWebベースである点は変わらず、巨大テキスト表示の改善には別途工夫が必要
- 「完全に依存のない単独exe」とは限らない

## その他の候補

### Python + PyInstaller

試作には向きますが、起動速度、配布容量、セキュリティソフトの誤検知、UIの作り込みを考えるとNotePaletteの本命にはしません。

### C++ + Qt

高速で高機能ですが、開発と保守の負担が大きく、Qtの関連ファイルも必要になりやすいため、現在の規模では過剰になりがちです。

### WinUI 3

新しいWindowsらしい外観を作れますが、配布とランタイム周辺はWPFより複雑になりやすいため、見た目を最優先する場合の候補とします。

## 比較表

| 項目 | Electron | C# + WPF | C# + Avalonia | Rust + Tauri |
|---|---|---|---|---|
| 現在の実装を活用 | 非常に高い | 低い | 低い | 中程度 |
| Windowsでの軽さ | 低め | 高い | 高い | 高い |
| 単独exe化 | 不向き | 適している | 可能 | 可能だが依存あり |
| UI開発の速さ | 高い | 中程度 | 中程度 | 中程度 |
| Windows機能との相性 | 中程度 | 非常に高い | 高い | 中程度 |
| 他OSへの展開 | 可能 | 不向き | 適している | 適している |
| 保守の分かりやすさ | 高い | 高い | 中程度 | 低め |
| NotePaletteとの相性 | 現在の最適解 | 将来の第一候補 | 複数OSが必要なら候補 | Web資産重視なら候補 |

## 移植を検討する目安

次のうち複数が実際の問題になった時点で、C# + WPF版の試作を検討します。

- 配布フォルダの大きさが日常的な負担になった
- 起動時間やメモリ使用量が気になる
- Electronの更新対応が保守負担になった
- 数十MB以上のテキストを頻繁に扱いたくなった
- Windowsとのより深い連携が必要になった
- 他の人へ継続的に配布する必要が生じた
- 現在の主要機能が固まり、UIを作り直しても仕様変更が少なくなった

単に「単独exeにしたい」という理由だけなら、全面移植に必要な時間のほうが大きくなりがちです。まず現在版で困っていることが実害になっているかを確認します。

## 移植する場合に守ること

### 1. データ形式を引き継ぐ

現在のデータは可能な限りそのまま読めるようにします。

- `board.json`: 配置、付箋、タブなどの情報
- `items/<itemId>/<tabId>.txt`: タブ本文
- `images/`: 画像
- `backups/`: 世代バックアップ
- `trash/`: ゴミ箱
- `window.json`: ウィンドウ状態

新しいアプリが旧データを直接読めない場合も、最初の起動時にコピーを作ってから変換します。原本を上書きしません。

### 2. 操作感を変えすぎない

- 自由配置とタイル表示
- 付箋内タブ
- 全体ズームと個別文字サイズ
- 自動保存
- ピン留め保護
- ドロップ取り込み
- 検索、収納、ゴミ箱、バックアップ
- 現在のショートカット

以上を移植版の最低限の互換範囲とします。

### 3. いきなり置き換えない

1. C# + WPFで小さな試作を作る
2. 起動速度、メモリ、配布容量、大容量テキストを比較する
3. 現行データをコピーして読み込む試験をする
4. 現在版と並行利用する
5. 十分に安定してから主利用を切り替える

## 推奨方針

当面は現在のElectron版を完成品として育てます。

将来、軽量化やWindows向け配布の簡潔さが明確な課題になった場合は、**C# + .NET + WPF**で小規模な互換試作を作り、実測してから移植を判断します。複数OSへの対応が必要になった場合のみ、AvaloniaまたはTauriを再評価します。

この方針なら、現在の使いやすさを失わず、必要になった時点でより軽い構成へ移れる余地を残せます。
